## FID 0Eh (Timestamp)

NVMe Feature FID `0Eh` — This feature enables the host to set a timestamp value in the controller. Timestamp lets the host read and optionally set the controller’s internal timestamp. In simple terms, **it gives the NVMe controller a notion of time, usually so that events, logs, telemetry, persistent event logs, and error records can be correlated with real-world time**. A controller indicates support for the Timestamp feature through the Optional NVM Command Support (ONCS) <!-- tags: #oncs --> field in the [[Identify Controller Data Structure]]. The timestamp is typically used by the controller for log pages, persistent event logs, telemetry, and other time-related records.

### What it does<br>
- Get Features, FID `0Eh`: Reads the controller’s current timestamp.
- Set Features, FID `0Eh`: Sets the controller’s timestamp, if the controller supports it.

The timestamp is commonly used as:
```
milliseconds since 1970-01-01 00:00:00 UTC
```
when initialized by the host.
### Why it matters<br>
Without the host setting FID 0Eh, the controller may not know the actual wall-clock time. Its timestamp may only count from reset or power-on.

By setting this feature, the host can make controller-generated records use a meaningful time reference.

Typical uses include:

- [[PEL (persisten event log)]] timestamps
- Error/event correlation
- [[Telemetry]] logs
- Debug and service analysis
- Matching drive events to host OS logs

#### Example
If the host sets the timestamp to:
```
1720000000000 ms since Unix epoch
```
the NVMe controller can use that value as its current time base. Later logs generated by the drive can include timestamps that align with real-world UTC time.

#### Support
Support is indicated in Identify Controller:<!-- tags: #oncs -->
```
ONCS bit 6 = 1
```
If this bit is set, the controller supports the Timestamp feature.

## 1. Feature summary

|Item|Description|
|---|---|
|Feature ID|`0Eh`|
|Feature name|Timestamp|
|Command Support|`Get Feature` and `Set Feature`|
|Scope|Controller-wide, not namespace-specific|
|Data size|8 bytes|
|Timestamp units|milliseconds|
|Timestamp width|48 bits|
|Endianness|Little-endian|
|Typical meaning|millisecond since 1970-01-01 00:00:00 UTC, if initialized by host|
|Saveable|Generally not a saved feature|
|Optional Support|Indicated by identify controller data|

## 2. Support discovery<br>
A controller indicates support for the Timestamp feature in the Identify Controller data.

In the Identify Controller structure: #oncs

|Field|Big|Meaning|
|---|---|---|
|`ONCS` - Optional NVM Command Support|Bit 6|Timestamp feature supported|

If not supported, a `Get Features` or `Set Features` command using FID `0Eh` will usually complete with an error such as Invalid Field in Command.

## 3. Command usage<br>
The Timestamp feature is accessed using the standard Admin commands:

|Command|Opcode|Purpose|
|---|---|---|
|Set Feature|`09h`|Set the controller stamp|
|Get Feature|`0Ah`|Get/read the controller stamp|

For both commands, the Feature Identifier is placed in command dword 10:
```
CDW10[7:0] = 0Eh
```
The timestamp value itself is transferred using an 8-byte data buffer.

## 4. Timestamp data structure<br>
The Timestamp feature uses an 8-byte data structure.

Returned by Get Features
```
Byte 0   Timestamp bits 7:0
Byte 1   Timestamp bits 15:8
Byte 2   Timestamp bits 23:16
Byte 3   Timestamp bits 31:24
Byte 4   Timestamp bits 39:32
Byte 5   Timestamp bits 47:40
Byte 6   Attributes
Byte 7   Reserved
```

Layout

|Offset|Size|Field|Description|
|---|---|---|---|
|0|6 bytes|Timestamp|48-bit timestamp in millisecond|
|6|1 byte|Attribute|Timestamp attributes|
|7|1 byte|Reserved|Reserved|

The 48-bit timestamp is little-endian.

## 5. Timestamp field<br>
The timestamp is a 48-bit value representing milliseconds. If the host has set the timestamp, it is normally expected to contain:

```
Milliseconds since 1970-01-01 00:00:00 UTC
```
This is effectively Unix epoch time in milliseconds.

Example:
```
Unix time: 1710000000000 ms
```
This value would be encoded as a 48-bit little-endian value in bytes 0 through 5.

Because the field is 48 bits wide, the maximum representable value is:
```
2^48 - 1 milliseconds
```
That is approximately 8,925 years of millisecond resolution.

## 6. Attribute byte<br>
Byte 6 of the Get Features response contains attribute bits.

|Bit|Meaning|
|---|---|
|`0`|Timestamp origin|
|`1`|Timestamp counting behavior|
|`7:2`|Reserved|

#### Bit 0 — Timestamp origin
|Value|Meaning|
|---|---|
|`0`|Timestamp was initialized by controller-level reset|
|`1`|Timestamp was initialized by Set Feature command|

- If bit 0 is `0`, the timestamp may simply represent elapsed milliseconds since the controller was reset.
- If bit 0 is `1`, the host has explicitly initialized the timestamp using Set Features.

#### Bit 1 — Counting behavior
|Value|Meaning|
|---|---|
|`0`|Controller counted time continuously since initialization|
|`1`|Controller may have stopped counting during vendor-specific intervals|

Bit 1 is important for determining whether the timestamp is suitable as a continuous monotonic time source.

For example, if a controller entered a deep low-power state and stopped its timestamp counter, bit 1 may indicate that the timestamp did not continuously advance.

## 7. Set Features behavior<br>
To set the timestamp, the host sends a Set Features command with FID `0Eh` and an 8-byte data buffer. For Set Features, the host provides the timestamp value in bytes 0 through 5.
```
Byte 0-5: 48-bit timestamp in milliseconds, little-endian
Byte 6-7: Reserved, should be zero
```
After a successful Set Features command, a subsequent Get Features command should report attribute bit 0 set to 1, indicating that the timestamp was initialized by the host.

## 8. Get Features behavior<br>
A Get Features command with FID `0Eh` returns the current timestamp data structure. The timestamp is not returned in the completion queue entry DW0. Instead, it is returned in the 8-byte data buffer associated with the command.

Example returned buffer:
```
E8 03 00 00 00 00 01 00
Therefore, Timestamp = 0x03E8 = 1000
```
Decode:
```
Timestamp bytes : E8 03 00 00 00 00 (0x3E8)
Timestamp value : 1000 ms
Attribute byte  : 01h
```
Attribute `01h` means:
```
Bit 0 = 1: Timestamp was initialized by Set Features
Bit 1 = 0: Controller counted continuously
```
So the timestamp is 1000 ms and was set by the host.

### EXAMPLE

This is decoding the **attribute byte** from the NVMe Timestamp feature buffer.

In your example, the attribute byte is:

```text
0x03
```

In binary:

```text
0x03 = 0000 0011
```

The Timestamp attribute byte is interpreted like this:

```text
Bit 0      = Synchronization bit
Bits 3:1   = Timestamp Origin
Bits 7:4   = Reserved
```

So for:

```text
0000 0011
```

label the bits:

```text
bit:   7 6 5 4 3 2 1 0
value: 0 0 0 0 0 0 1 1
                         ^
                         bit 0
```

### `bit 0 = 1`

Bit 0 is the least significant bit.

Since `0x03` is binary `0000 0011`, bit 0 is `1`.

That means:

```text
Synchronization bit = 1
```

So the controller indicates it has counted time continuously since the timestamp was initialized.


### `origin = (0x03 >> 1) & 0x7 = 1`

This extracts bits `3:1`.

#### Step 1: Shift right by 1

```text
0x03 >> 1
```

Binary:

```text
0000 0011 >> 1 = 0000 0001
```

So:

```text
0x03 >> 1 = 0x01
```

This moves bits `3:1` down into bit positions `2:0`.

#### Step 2: Mask with `0x7`

```text
0x01 & 0x07
```

`0x7` in binary is:

```text
0x07 = 0000 0111
```

The mask keeps only the lowest 3 bits:

```text
  0000 0001
& 0000 0111
-----------
  0000 0001
```

So:

```text
(0x03 >> 1) & 0x7 = 0x01
```

Decimal:

```text
0x01 = 1
```

Therefore:

```text
origin = 1
```

Meaning:

```text
Timestamp was initialized using a Set Features command
```



In short:

```text
attr = 0x03 = 0000 0011

bit 0 = 1
bits 3:1 = 001b = 1
```

So the decoded meaning is:

```text
Synchronization = 1
Origin          = 1, set by Set Features
```

## 9. Reset and power behavior<br>
After a controller-level reset, the timestamp may be reinitialized by the controller. If the host has not set the timestamp after reset, the controller may report:

```
Attribute bit 0 = 0
```

This means the timestamp was initialized by the reset, not by the host. In that case, the timestamp value may represent time elapsed since reset rather than real UTC epoch time. The host should set the timestamp after initialization if it wants the controller to have a real wall-clock time reference.

## 10. Practical usage<br>
A typical host sequence is:

1. Identify the controller.
2. Check whether ONCS[6] indicates Timestamp support.
3. During initialization, calculate current Unix epoch time in milliseconds.
4. Issue Set Features FID `0E`h with that value.
5. Later, use Get Features FID `0Eh` to check the controller timestamp.

## 11. Example: preparing a timestamp buffer<br>
Current time in milliseconds can be generated in Python:
```
import time

ts = int(time.time() * 1000)

# 8-byte little-endian buffer.
# Current epoch milliseconds fit in the lower 48 bits.
buf = ts.to_bytes(8, byteorder="little")

with open("timestamp.bin", "wb") as f:
    f.write(buf)
```

## 12. Example with `nvme-cli`<br>
Read the timestamp:

```
nvme get-feature /dev/nvme0 -f 0x0e -l 8 -H
```

Set the timestamp using an 8-byte data buffer:

```
nvme set-feature /dev/nvme0 -f 0x0e -l 8 -d timestamp.bin
```

Exact command options may vary slightly depending on the `nvme-cli` version.

## 13. Important notes<br>
- FID `0Eh` is controller-wide.
- The timestamp is 48 bits, not 64 bits.
- The data buffer is 8 bytes, but bytes 6 and 7 are not part of the timestamp value.
- Byte 6 contains attributes when reading the feature.
- When setting the feature, reserved bytes should be cleared.
- The timestamp is in milliseconds.
- The feature is useful for log correlation but should not be treated as a secure clock.
- If the controller reports that it may have stopped counting, timestamp continuity is not guaranteed.
